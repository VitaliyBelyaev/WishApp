# Релиз Android-приложения

Как выпускать «Хотелки» в Google Play: ветки и теги, проверки перед релизом,
раскатка. Других сторов нет. iOS на паузе, здесь только Android.

## Ветки и теги

- `dev` — основная разработка, сюда вливаются feature-ветки.
- `master` — то, что сейчас в проде. Сюда попадает только раскатанный релиз.
- `release/android-X.Y.Z` — ветка релиза, живёт от сборки до полной раскатки.
- Тег `android/vX.Y.Z` — коммит, из которого собран бандл, ушедший в прод.
  Префикс обязателен: теги iOS идут как `ios/vX.Y.Z`.

Раньше релизили прямо из `dev`, ветку релиза не отводили. Ветка нужна, потому что
раскатка идёт несколько дней, а `dev` за это время уходит вперёд, например
задачами редизайна. Исправление для релиза делается в его ветке, и
недоделанное из `dev` в прод не попадает.

### Шаги

1. Отвести ветку от `dev`:

   ```bash
   git switch dev && git pull
   git switch -c release/android-X.Y.Z
   ```

2. Сразу поднять `versionName` и `versionCode` в `app/build.gradle.kts` до
   итоговых и закоммитить: `Update app version to X.Y.Z (N)`. `versionCode`
   всегда больше прошлого загруженного в Play, даже если ту сборку не выпустили.
3. Быстрые проверки на debug-сборке (раздел ниже). Не прошли — исправить в ветке
   релиза и повторить.
4. Подложить боевые файлы (раздел «Боевые файлы перед сборкой») и собрать
   релиз-кандидат: бандл для Play и APK для проверок, оба подписаны ключом
   загрузки. После сборки проверить Firebase-проект, ключ Amplitude и подпись.
5. Проверки на релиз-кандидате: smoke-тест, скриншот-тест и ручной проход.
   Нашлась ошибка — исправить в ветке и вернуться к шагу 3. Если бандл уже
   загружали в Play, поднять `versionCode`.
6. Загрузить бандл во внутреннее тестирование и проверить обновление поверх
   версии из Google Play.
7. Когда сборка уходит в прод, поставить тег на коммит, из которого она собрана,
   и запушить ветку с тегом:

   ```bash
   git tag -a android/vX.Y.Z -m "Android X.Y.Z (N)"
   git push origin release/android-X.Y.Z android/vX.Y.Z
   ```

   Если после этого понадобилась новая сборка, это уже следующая версия
   `X.Y.Z+1` со своим тегом, тег не переносится.
8. После полной раскатки влить релиз в `master`, затем `master` в `dev`:

   ```bash
   git switch master && git pull && git merge --no-ff release/android-X.Y.Z
   git switch dev && git pull && git merge master
   git push origin master dev
   git branch -d release/android-X.Y.Z && git push origin --delete release/android-X.Y.Z
   ```

   Ветку можно удалять: тег остаётся.

### Срочное исправление

Если в проде нашлась ошибка, а в `dev` уже лежит то, что выпускать нельзя:
отвести `release/android-X.Y.Z+1` от тега текущей версии, исправить, дальше те же
шаги. Исправление попадёт в `dev` через слияние `master`.

## Проверки перед релизом

Полного набора автотестов нет, поэтому проверки идут в два захода. Сначала
быстрые на debug-сборке, чтобы не собирать релиз зря. Потом те же тесты и ручной
проход на релиз-кандидате: в нём работает R8, и ошибки минификации видны только
там.

### Быстрые, на debug-сборке

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:lintDebug
./gradlew :shared:compileKotlinIosArm64 :shared:linkDebugFrameworkIosSimulatorArm64
scripts/run_smoke_test.sh
```

- Всё должно проходить без ошибок.
- `run_smoke_test.sh` — быстрый успешный сценарий по основным экранам. Он стирает
  данные приложения и по умолчанию запускается на отдельном эмуляторе
  `WishApp_Screenshots`.
- `:shared:allTests` идёт через iOS-симулятор, прогонять по желанию.

### Боевые файлы перед сборкой

Три файла в git не лежат, их надо подложить из своего хранилища перед каждой
release-сборкой. Ошибки сборка не даст ни по одному: без них соберётся
работающий APK, который шлёт данные не туда или подписан не тем ключом.

| Файл | Куда положить | Без него |
|---|---|---|
| Боевой `google-services.json` | `app/src/google-services.json` | Crashlytics, Firebase Analytics и Performance уйдут в тестовый проект `wishapp-debug`, туда же загрузится маппинг R8 |
| `apikey.properties` с `AMPLITUDE_API_KEY=...` | корень проекта | ключ Amplitude пустой, аналитика молча не работает |
| Ключ загрузки `wish_app_release_keystore` и пароли | `app/wish_app_release_keystore`, пароли в менеджере паролей | Gradle подпишет тестовым `test_keystore`, Play такой бандл не примет |

- В `app/google-services.json` (лежит в git) тестовый проект `wishapp-debug`.
  Боевой кладём рядом, в `app/src/google-services.json`: если есть оба, плагин
  берёт файл из `app/src/`. Тестовый не трогаем.
- В боевом нет пакета `.debug`, его же использует `autotest`. Пока он лежит в `app/src/`,
  debug-сборка и автотесты не соберутся. После release-сборки убрать его
  обратно в хранилище.
- Все три пути в `.gitignore`. Перед коммитом всё равно проверить `git status`.
- Ключ Amplitude в `apikey.properties` один на все сборки, debug тоже его читает.

Проверка после сборки (команды ниже):

```bash
# Firebase: должен быть боевой project_id, не wishapp-debug
grep -E 'project_id|google_app_id' app/build/generated/res/processReleaseGoogleServices/values/values.xml

# Amplitude: значение не пустое
grep AMPLITUDE_API_KEY app/build/generated/source/buildConfig/release/ru/vitaliy/belyaev/wishapp/BuildConfig.java

# Подпись: SHA-256 совпадает с сертификатом ключа загрузки
# (Play Console → Тестирование и выпуск → Целостность приложения → Подпись приложения)
keytool -printcert -jarfile app/build/outputs/bundle/release/app-release.aab | grep SHA256
apksigner verify --print-certs app/build/outputs/apk/release/app-release.apk | grep SHA-256
```

### Сборка релиз-кандидата

Собирать в Android Studio: Build → Generate Signed App Bundle or APK, ключ
`app/wish_app_release_keystore`, вариант `release`. Сначала бандл, потом APK.

- `./gradlew :app:bundleRelease` для релиза не годится: `signingConfig` в
  `release` — тестовый `test_keystore`, Play такой бандл не примет.
- Бандл уходит в Play, APK с того же коммита — для проверок.
- После сборки — проверка из раздела выше: Firebase, Amplitude, подпись.
- Если в зависимостях появились новые `.so`, проверить выравнивание 16 КБ:
  `zipalign -c -P 16 -v 4 <apk>`.

### На релиз-кандидате

```bash
BUILD_TYPE=autotest scripts/run_smoke_test.sh
scripts/take_screenshots.sh ru,en light,dark
```

- Smoke-тест идёт на сборке `autotest`: она как `release`, с теми же правилами
  R8, но подписана тестовым ключом и с тем же id, что у debug
  (`ru.vitaliy.belyaev.wishapp.debug`): поставится поверх debug-сборки. Он ловит то, что R8 вырезал или
  переименовал, а на debug этого не видно. Сам подписанный кандидат тест не
  гоняет: тестовый APK пришлось бы подписывать ключом загрузки.
- Перед прогоном боевой `google-services.json` должен быть убран из `app/src/`,
  иначе `autotest` не соберётся.
- Прогон только на эмуляторе с Android 8 (API 26) и выше: в прогоне `autotest`
  выключен desugaring `java.time`, почему — в `app/build.gradle.kts`.
- Тест вызывает напрямую несколько классов приложения, для них есть keep-правила
  в `app/proguard-autotest.pro`. В релиз они не попадают. Новые правила туда
  добавлять только для того, что тест трогает в обход интерфейса.
- Скриншот-тест подменяет экранам зависимости и трогает много внутренностей,
  поэтому он идёт только на debug и лежит в `app/src/androidTestDebug/`.
- `take_screenshots.sh` прокликивает почти все экраны и состояния, поэтому ловит
  падения и сломанную вёрстку. После прогона посмотреть изменения в
  `docs/screenshots/` через `git diff`: что поменялось и ожидаемо ли это.
  Скриншоты закоммитить в ветку релиза.

Ручной проход, основной сценарий:

- Создать хотелку: название, описание, ссылка, ярлыки, фото.
- Отметить выполненной и вернуть обратно, отменить через снекбар.
- Сортировка и ручной порядок, фильтр по ярлыку.
- Редактирование и удаление ярлыков.
- Просмотр фото, удаление фото.
- Поделиться текстом и PDF.
- Бэкап в Google Drive и восстановление.
- Тема, экран «О приложении», лицензии, политика конфиденциальности.

### Обновление поверх прода

Самое важное при миграциях БД. Локальная сборка подписана другим ключом и поверх
версии из Play не встанет, поэтому через внутреннее тестирование:

1. Поставить текущую версию из Google Play, создать несколько хотелок с ярлыками,
   ссылками, фото и выполненными.
2. Обновиться сборкой из внутреннего тестирования.
3. Данные на месте, приложение не падает.

### Если поднимался `targetSdk`

Android меняет поведение по целевому уровню API. Для перехода на 35–37:

- Edge-to-edge обязателен: ничего не залезает под статус-бар, жестовую панель и
  клавиатуру, на всех экранах и в обеих темах.
- Predictive back включён по умолчанию: жест назад с каждого экрана и из шторок.
- На экранах шире 600 dp система игнорирует запрет поворота и ограничения
  размера окна: проверить планшет или складной эмулятор в обеих ориентациях.
- Самая старая поддерживаемая версия (`minSdk 24`, Android 7) запускается и
  проходит основной сценарий.

## Раскатка в Google Play

1. Внутреннее тестирование: загрузить бандл, проверить обновление поверх прода
   (шаг 6).
2. Производственная версия: заметки о выпуске минимум на русском и английском.
3. Поэтапная раскатка: сначала 5–10%, пару дней смотреть Crashlytics и Android
   vitals. Всё в порядке — 50%, затем 100%. Новые падения — остановить раскатку и
   выпустить исправление следующей версией.
4. Проверить «Соответствие правилам» в Play Console: требования к `targetSdk`
   меняются каждый год, сроки обычно 31 августа.
5. После 100% — слить ветки (шаг 8 выше).
